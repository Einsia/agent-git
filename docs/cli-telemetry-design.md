# CLI product telemetry

Status: design rationale. The implemented collection contract and operational
limits are documented in [CLI usage statistics](telemetry.md); the checked-in
[`registry.json`](../src/telemetry/registry.json) is the authoritative field inventory. Deployment
and production ingestion are separate from the local implementation.

Source baseline: CLI `cf4f1abdcd401d31bd7154fed27a951980885ed4`.
The command inventory below covers all 41 top-level CLI commands at that revision,
including hidden entry points. Backend and Hub references describe inspected source,
not verified production ingestion.

## Product decisions

AgentGit should measure feature adoption, active accounts, command outcomes, and
performance across the CLI, its integrations, and the Hub. Usage statistics are
required for the official production Hub. Other Hubs retain optional setup
preferences and need an explicit analytics destination. The Hub policy below
applies to both ordinary commands and installer receipts.

Statistics include the signed-in account ID. They are account-linked product
analytics, not anonymous analytics. Repository contents, user-written text,
credentials, and resource identifiers are outside the collection contract.

The governing rule is an explicit field allowlist, not "serialize everything except
known secrets." A value being non-textual, generated by a machine, or represented
by a UUID does not establish that it is safe. Account identity and telemetry's own
random identifiers are deliberate exceptions; repository, workspace, native session,
PR, secret-record, and remote-connection identifiers are excluded.

Default-on and acceptance through an installer are recorded as preference sources.
They must not be labeled explicit legal consent. Applicable notice, legal-basis,
processor, retention, and withdrawal requirements remain separate release concerns.
This proposal does not amend the published Privacy Policy.

## Hub policy and onboarding

The current behavior is specified in [CLI usage statistics](telemetry.md).
Statistics are required for the official production HTTPS Hub (`agent-git.com`
and `www.agent-git.com` on the default port). A valid ordinary command, integration
or verified installer initializes this policy without an opt-in prompt. Saved
refusals and environment opt-outs do not apply there. Hidden official npm installs
record verified receipts without waiting for a visible terminal.

The selected Hub must be passed through collection, acquisition and transport,
including the explicit `login --hub` override. Existing enabled installation
identities and deduplication remain stable. Migrating a disabled state starts a
new generation so old collectors cannot append to it. The persisted decision
source is `hosted_hub` and the event mode is `required`.

Other Hubs keep optional preferences and environment overrides, and never inherit
the official analytics destination. Local commands buffer events without making
network requests. Help, version, invalid commands, completion generation and
maintenance setup remain lightweight. There is no telemetry subcommand; inspect
the source registry for the field inventory.

## Event model and common properties

Use a small, stable event vocabulary. Operation names and properties provide detail;
do not create an event name per arbitrary argument, error message, or resource.

| Event | Meaning |
| --- | --- |
| `cli_command_started` | A recognized external invocation has entered its execution path |
| `cli_command_finished` | That invocation returned, was rejected, or was observably cancelled |
| `cli_operation_finished` | A named product operation reached a meaningful result inside the invocation or daemon |
| `cli_integration_summary` | Aggregated hook, polling, or connection activity over a bounded interval |
| `cli_onboarding_completed` | Enabled onboarding completed, with installation and decision sources |
| `cli_session_started` | A telemetry activity session began; not an agent conversation |

Nonproduction installations with a disabled preference do not upload analytics. Do not
claim a complete acceptance rate from received events: the rejection denominator
is intentionally unobserved.

Top-level properties shared with Hub retain their meanings where appropriate:

| Property | Type and rule |
| --- | --- |
| `schema_version` | Versioned telemetry contract, initially `1` |
| `event_id` | Fresh random UUID; reused unchanged on retry |
| `event_ts` | UTC occurrence time in milliseconds, not upload time |
| `client_type` | `cli`; daemon events additionally carry their integration source |
| `pver`, `cli_version` | Validated build version; exclude custom build metadata and branch names |
| `app_env` | Compatibility with Hub: `production` or `development` |
| `deployment_env` | `production`, `staging`, `development`, `self_hosted`, `unknown` |
| `release_channel` | `stable`, `prerelease`, `development`, `unknown` |
| `user_id` | Authoritative signed-in Hub `account_id`, or absent |
| `identity_state` | `identified`, `signed_out`, `signed_in_id_missing`, `unavailable` |
| `device_id` | Random local telemetry installation identifier; no hardware fingerprint |
| `session_id` | Random telemetry activity-session ID; never a native or AgentGit session ID |
| `invocation_id` | Random ID for one external CLI or MCP action |
| `parent_invocation_id` | Optional validated telemetry-only parent ID for internal children |
| `operation_id` | Random ID for a semantic operation when needed |
| `is_first_visit` | First telemetry activity session for this local analytics identity, not proof of first-ever use |
| `channel` | Fixed installation channel: `create_agit`, `npm_global`, `source`, `archive`, `unknown` |
| `language` | Normalized supported language code, else `unknown`; not a raw locale string |
| `os`, `arch` | Closed enum: supported OS and CPU architecture categories |
| `os_version_major` | Optional validated major release number; not a full OS build string |
| `telemetry_mode` | `required`, `default_on` or `explicit_enable`; not a legal-consent claim |
| `notice_version` | Fixed shipped disclosure version |
| `sample_rate` | Included probability for sampled events; `1` for unsampled command lifecycle events |

Do not copy Hub's `username`, email, landing URL, referrer, UTM strings, social
profile, or inferred country into the CLI. Most have no CLI equivalent or are
user-controlled text. Omit `web_version` on a CLI event. Derive dates from `event_ts`
in the analysis layer using an explicit timezone.

Use a shared activity-session record for CLI processes on the same installation
and current analytics principal. Start a new session after 30 minutes of inactivity,
at a UTC date boundary, after account switching, or after telemetry is disabled and
enabled again. Update it under the telemetry-state lock; parallel commands must not
each count as a new visit. Background keepalives do not extend an activity session.
Session and installation identifiers are never reused as AgentGit session targets.

The inspected Hub maps staging to `app_env=development`. Keep this compatibility
field and add `deployment_env` so staging does not disappear into local development.
A separate change can align the Hub with the additional property.

### Invocation and environment properties

| Property group | Allowlisted information |
| --- | --- |
| Command | Canonical top-level command, subcommand path, fixed invoked alias, semantic action |
| Output | `text`, `json`, `tui`, `mcp`; requested JSON version; quiet/no-color flags |
| Terminal | Independent `stdin_tty`, `stdout_tty`, `stderr_tty`; prompt capability; whether a prompt actually appeared |
| Caller | `direct`, `agent`, `hook`, `mcp`, `rc`, `installer`, `unknown`, with `source_confidence` |
| CI | Boolean and allowlisted provider such as GitHub Actions or GitLab CI, else `other`/`unknown` |
| Agent environment | Presence of known runtime markers; runtime enum or `multiple`/`unknown` |
| AgentGit environment | `agit_session_env_present`, `agit_session_state`, `agit_merge_env_present`, `rc_mode`, `protocol_child` |
| Managed context | `managed`, `unmanaged`, `unknown`, based on already-performed product resolution; separate from an environment hint |
| Hub | `official` or `self_hosted`, environment class, auth state; never URL, host, account email, or token |
| Runtime selection | Requested/effective runtime enum and `argument`, `config`, `picker`, `unknown` selection source |
| Target selection | `explicit`, `agit_environment`, `picker`, `none`, `unknown`; target shape only |
| Workspace | Already-known code-Git presence, bound/unbound, regular checkout/worktree/unknown; no path, origin, branch, or Git status dump |
| Hardware | Optional CPU-count and RAM-size buckets, only if cheap platform APIs supply them |
| Execution result | Stable exit category/code, semantic outcome, fixed failure stage, duration bucket, cancellation kind |

TTY, CI, and agent execution are independent dimensions. A PTY is not proof of a
human operator, and `--yes` is not proof of CI. Do not inspect process command lines
or scan the environment to guess the parent application. Use explicit integration
markers when AgentGit launches a child; classify other evidence as a hint.

Current managed-session routing uses `AGIT_SESSION`, not `AGIT_SESSION_ID`.
`AGIT_SESSION_ID`, if present, can be represented by a presence-only diagnostic
flag, but must not establish session ownership. The values of both variables are
excluded. A syntactically valid `AGIT_SESSION` is only an environment hint; it can
be stale, and absent does not establish that a native conversation is unmanaged.

Known runtime marker names should reuse `infra::runtime_session::ENV_SESSIONS`.
Telemetry must not cause native transcript discovery or inspect session contents
just to fill an environment field. Missing facts remain unknown.

### Identity across CLI and Hub

Use `account_id` returned by authentication, never username, email, token contents,
Git author identity, MAC address, or the repository owner's ID. Add an optional
`account_id` to CLI `LoginResponse` and `HubCredential`, preserving it through refresh.
The inspected backend already returns this field; the current CLI drops it.

For existing credentials without an account ID, acquire it during a normal explicit
login, `whoami --check`, or a compatible authenticated response already requested
by the product. Do not add a per-command `whoami` request, refresh expired credentials,
scan other Hub credential files, or trigger a Keychain prompt for analytics alone.
Until refreshed, emit `identity_state=signed_in_id_missing` without `user_id`.

Maintain a minimal account-ID cache when authentication changes so analytics does
not deserialize token-bearing credentials on every local command. Bind that cache
to the selected normalized Hub authority and update it atomically with login/logout.
No raw authority is included in the outgoing event.

For the official production project, use the same account ID as Hub's PostHog
`distinct_id`. Before sign-in, use a namespaced random telemetry identity. Never
merge two authenticated accounts through a shared device ID. Rotate the anonymous
identity and activity session across logout/account switches; do not retroactively
rewrite queued events. Capture principal identity at event occurrence time.

Do not automatically alias all pre-login activity into an account profile. An
installation-to-login funnel can use a narrowly scoped telemetry onboarding ID;
cross-account linkage must not be inferred. Non-production identities need separate
projects or coordinated namespaces in both CLI and Hub to prevent collisions.

RC separates the local signed-in connection owner from a verified remote actor.
Use an optional `actor_user_id` only when the product has authenticated attribution
and the applicable operator/workspace analytics policy permits it. Otherwise record
`actor_kind=remote_operator|owner|system|unknown` and omit that ID. A machine owner's
preference must not silently establish consent on behalf of every collaborator.
Never derive the actor from prompt text, workspace names, or client-supplied labels.

## Field classification

Every command argument must have one explicit disposition in a reviewed registry:

| Class | Rule |
| --- | --- |
| Boolean | Record true/false, plus whether supplied explicitly when meaningful |
| Enum | Record only a canonical member of a finite published vocabulary |
| Numeric setting | Range-check; retain a safe bounded configuration value or map to a documented bucket |
| Presence | Record only whether the user provided the field, never its value, length, or hash |
| Count | Count a list or product result, then bucket it; never retain elements |
| Excluded | Do not inspect or serialize the value for analytics |

These classifications are not inferred from Rust `String`, `u64`, or UUID types.
For example, a PR ID is a number but remains excluded; visibility is presently a
string but can safely map to `public|private|invalid`. An unknown enum value maps to
`invalid` without echoing the supplied text. Unknown command and flag names are
also user input, not approved analytics dimensions.

Defaults and explicit selection must be distinguishable. Record requested and
effective values only when both are approved, and identify a config/default source
using an enum without copying the configuration document.

All booleans in the inventory below are approved unless explicitly excluded.
Optional target/path/text fields produce only presence indicators. Lists of paths,
refs, branch selectors, or queries produce only count buckets. The classifier does
not read the files referenced by those arguments.

Proposed standard buckets:

- Counts: `0`, `1`, `2-5`, `6-20`, `21-100`, `101-1000`, `1001+`.
- Duration: `<10ms`, `10-49ms`, `50-199ms`, `200-999ms`, `1-4s`, `5-29s`, `30-119s`, `2m+`.
- Transfer size: `0`, `<1KiB`, `1-63KiB`, `64-1023KiB`, `1-15MiB`, `16-255MiB`, `256MiB+`.
- CPU cores: `1`, `2`, `3-4`, `5-8`, `9-16`, `17+`; RAM: `<4GiB`, `4-7GiB`, `8-15GiB`, `16-31GiB`, `32GiB+`.

Exact durations can be a separately reviewed performance-metrics extension. The
initial product-analytics contract uses duration buckets and client time rounded
to a minute for ordinary events, with telemetry IDs preserving lifecycle linkage.
Transfer counts and sizes reuse results the operation already computes; telemetry
must not walk a repository to measure them.

### MCP, TUI, hooks, and remote control

Current MCP tools are `search`, `show`, `view`, `status`, `commit`, `rc_status`, and
`rc_list`. Map them onto the corresponding canonical CLI operation. The wrapper
currently spawns CLI subprocesses; pass an analytics-only invocation context so the
wrapper and child do not count the same operation twice. Attribute schema rejection
to the wrapper when no child starts. Unknown tool names become `unknown`, not raw
text. Do not record MCP client-provided names, protocol request IDs, or arguments.

TUI records fixed screen IDs, entry/exit, confirmed actions, and cancellation. Do
not record keypresses, selected row text, search input, focus coordinates, or a
screen recording. Opening a picker is distinct from completing a resume/share action.

Hooks aggregate ordinary ingest/settle/no-op counts by runtime, outcome, and duration
bucket over a short window. Typed failures and meaningful state changes can emit
individual operation events. A hook callback is not a human command or daily-active
user. Stop/session events contribute only fixed event categories, not payloads.

RC additionally covers pair/start/stop, connection/reconnect, session preparation,
runtime launch/end, settlement, automatic push, and approval requested/decided.
Record fixed capability category, actor role, approval outcome, error stage, and
count/duration buckets. Arbitrary terminal commands, instructions, approvals' command
strings, tool arguments, terminal output, workspace paths, and streamed session
events never enter analytics. No event per terminal character or WebSocket frame.
Fixed per-method in-memory counters aggregate remote requests. A background worker
persists summaries outside the daemon event loop and revalidates the captured
identity and consent generation. Disabling statistics invalidates delayed counts;
daemon exit can discard counts that have not been persisted.

## Instrumentation architecture

```text
CLI parser / MCP dispatcher / hook / TUI / RC product operation
    -> typed command and operation descriptors
    -> reviewed field policy and enum normalization
    -> preference + destination + identity snapshot
    -> validated TelemetryEvent
    -> bounded local queue
    -> sender with a fresh preference-generation check
    -> PostHog ingestion
```

Do not feed existing CLI echo, JSON output envelopes, debug representations, session
transcripts, log records, or `anyhow` error chains into this path. Those objects can
legitimately contain private material. A sanitizer appended to an unrestricted
payload is not the collection boundary.

Place CLI instrumentation behind the `cli` feature. Backend builds using this crate
with `default-features=false` must not acquire product telemetry or a sender.
Keep the semantic descriptor separate from HTTP transport so privacy tests can run
without networking or global configuration.

Use a declarative registry keyed by canonical command/subcommand/argument ID.
Every Clap argument has a classification, including excluded ones. Enum serializers
produce their own fixed literals; unknown values cannot become strings in an event.
An exhaustive Rust match covers `Commands`; metadata tests compare the complete
Clap tree, nested variants, aliases, and argument IDs against the registry.
Adding a command or flag without a policy must fail the coverage check.

`main.rs` currently uses `process::exit` on several paths. Explicitly finish the
telemetry span before normal exit: RAII Drop alone does not run on process exit.
Cover parse failure, startup rejection, JSON incompatibility, bare-TUI dispatch,
normal success, and typed terminal failure. Parse failure handling must obtain
only validated static command IDs and `clap::ErrorKind`, never `error.to_string()`.

Started and finished events share an invocation ID but have separate event IDs.
Finished events include result dimensions and can stand alone if the start is lost.
`SIGKILL`, abrupt machine loss, and some signal exits cannot promise a finish event.
Do not report these as successful or infer a crash solely from a missing finish;
queue loss and sampling can also explain it. Do not change SIGPIPE semantics.

Semantic events report fixed stages such as `parse`, `startup`, `target_resolution`,
`authentication`, `scan`, `local_write`, `network`, `runtime_prepare`, `runtime_launch`,
and `finalize`. Exit categories follow `ExitCode`: success, failure, usage, reference,
precondition, authentication, network, policy, and interaction-required. HTTP status
codes are safe only as numeric status/status-class, without response detail or URL.

No-op, partial completion, queued settlement, successful runtime preparation, and
actual child-process launch are distinct outcomes. Where exit status alone cannot
distinguish them, add an explicit typed product result. Never parse terminal text
to infer success or failure.

A non-interactive login can issue an authorization link successfully without
signing in. Record `authorization_issued`, then `pending`, `expired`, `denied`, or
`authenticated` when completion is attempted. Only persisted authenticated identity
qualifies as successful login in an activation funnel. Never use the authorization
state as a telemetry correlation ID; correlate eligible attempts through a separate
locally generated analytics ID without transmitting the state or URL.

### Local and offline behavior

All eligible commands can contribute sanitized local events, but local commands
must not initiate telemetry network traffic just because they ran. This preserves
the CLI's offline and read-only request behavior, particularly `search --local`,
status, diff, doctor, and scoped review paths.

Drain queued events on a permitted online operation or an already-running,
configured integration sender. Local-only commands do not start a background
network worker. They can therefore be represented later, when a permitted upload
occurs. Offline-only installations may never appear in PostHog; that is a known
coverage limit, not a reason to silently override offline behavior.

Nonproduction unconfigured, disabled, or no-destination states allocate no analytics identity,
enqueue no data, and make no telemetry request. Preference inspection does not
migrate the AgentGit store, scan Git state, launch a runtime, or acquire credentials.

### Queue and transport

Initial proposed limits, to be validated before implementation ships:

- Queue cap: 1 MiB or 1,000 events, whichever is reached first.
- Event cap: 8 KiB with bounded property keys and values; oversized events are dropped.
- Queue TTL: 24 hours; expired events are discarded rather than uploaded later.
- Batch cap: 50 events; serialized sender under a cross-process lock.
- Hook summary interval: 60 seconds; no persistent duplicate raw callback stream.
- Retry transient failures with exponential backoff; cap attempts and respect TTL.
- Foreground command completion waits at most 100 ms for any telemetry handoff;
  telemetry failure never changes its exit code. Network work belongs outside that
  foreground budget and must have its own bounded connect/request timeout.

Use private file permissions and atomic writes, with the platform equivalent of
0700 directories and 0600 files. Telemetry state is excluded from session archival,
AgentGit artifacts, ordinary file commits, and automatic synchronization.
Payloads contain only the typed allowlist, even on disk.

Retry with the same event UUID and occurrence timestamp. Verify PostHog duplicate
handling in an isolated project rather than assuming an event property named ID
provides deduplication. Track local dropped-count summaries without recursively
generating telemetry about telemetry failures.

The sender rechecks disabled state and generation both before dequeue and before
network admission. `disable` synchronizes with that admission gate so an old daemon
cannot upload after observing an earlier enabled state. Global overrides also
disable queue draining. Children inherit force-off; enabling never overrides an
administrator or environment-level refusal.

For the official CLI, use a configured analytics endpoint and public ingestion key;
never send Hub authentication tokens to PostHog. Do not use an authenticated Hub
client as the telemetry HTTP client. Disable redirect following that could change
the destination, and do not fall back to another endpoint after refusal.

A dedicated first-party collector is an optional deployment choice if server-side
schema validation or IP suppression is required; a proxy alone does not anonymize
traffic. Network recipients necessarily see connection metadata. Disable unnecessary
IP retention and geolocation, avoid forwarding identifying headers, and define
ingress-log retention separately. Verify the actual ingest configuration.

Self-hosted/custom Hubs must not silently report their accounts to the production
PostHog project. Use a separately configured destination and operator policy; without
one, effective sending is off even if the general local preference is enabled.
This is a destination boundary, not
an exception that silently re-enables a user-level refusal.

## Analysis and retention

Define human activity separately from automation and background activity:

- Account DAU/WAU: distinct `user_id` with a foreground or user-requested product
  action; exclude keepalives, status polling, telemetry controls, and no-op hooks.
- Automated adoption: accounts and installations with useful agent/MCP/RC actions,
  reported as a separate cohort, not added to human DAU by counting events.
- Activation: enabled setup -> login -> first successful import/new -> first settled
  content -> first push -> first Hub view. Identity gaps are visible, not guessed.
- Feature adoption: unique accounts using a semantic operation, by version/runtime,
  caller source, and environment; compare explicit enum selections with defaults.
- Reliability: failures divided by eligible attempts within the same command and
  context; break down typed stage/category and distinguish partial outcomes.
- Performance: duration distributions by operation/version/platform; account for
  bucket resolution, sampling, missed finishes, and offline upload delays.

Do not count started and finished as two uses. A parent MCP request and its CLI
child form one external action; automatic push is a distinct semantic operation,
not another human invocation. Installer version checks and repeated idempotent setup
do not create new installations.

Proposed storage policy: retain account-linked raw events for 90 days, then delete;
retain truly aggregated product statistics for 12 months. Aggregates must remove
account/device/activity identifiers and avoid tiny identifying groups. These are
implementation targets requiring configured retention and deletion verification,
not claims about the current PostHog project. Access to account-level drilldown is
limited to authorized product/support staff with access auditing. It is not an
employee surveillance or automated eligibility signal.

For nonproduction Hubs, disabling future telemetry and historical deletion are distinct controls.
Account deletion must include analytics identity and related events according to
the applicable policy. Changing the PostHog identity strategy must not leave an
untracked anonymous alias outside the deletion scope.

## Verification and delivery

The implementation is complete only when these properties have evidence:

1. The registry covers every current Clap command, alias, subcommand, and argument,
   plus the MCP tool schema. An unclassified addition fails the coverage check.
2. Canary private text injected into argv, unknown flags, malformed enums, paths,
   URLs, messages, errors, hook payloads, and MCP bodies never appears in a queue,
   event, sender log, or upload. Numeric identifiers and token-like values are
   included in adversarial cases. Privacy validation happens before persistence.
3. Official Hub mandatory setup, nonproduction `[Y/n]`, cancellation, non-TTY, `--yes`, actual
   `npx -y create-agit`, global npm postinstall, reinstall, upgrade, and prior refusal
   obey the selected Hub policy. Both npm lifecycle ordering and terminal output are checked.
4. Official Hub legacy refusals and environment overrides cannot disable capture.
   Nonproduction refusal, queued data, concurrent CLI processes,
   running MCP/RC senders, environment overrides, corrupt config, and unwritable
   state respect the installation generation and nonproduction disable boundary.
5. Account-ID capture, old credentials, token refresh, account switching, logout,
   multiple Hub authorities, self-hosting, and remote-operator attribution never
   cross principal boundaries or copy authentication tokens.
6. CLI text/JSON exit behavior, MCP framing, hook output, completion output, SIGPIPE,
   and offline/local-only request behavior remain correct with telemetry on/off.
7. Root lifecycle, early errors, semantic no-op/partial/deferred outcomes, TUI
   cancellations, MCP subprocesses, RC child launches, and hook aggregation have
   distinct, non-duplicated events.
8. Fake transport verifies caps, TTL, retries, event identity, slow/unavailable
   endpoints, and disabled generations without contacting production analytics.
9. An isolated PostHog project receives synthetic events with correct identity,
   timestamps, deduplication, environment filtering, IP handling, and deletion.
   Local unit tests or a successful HTTP response alone do not prove this.

Implement in focused verified commits: preference/onboarding; account-ID plumbing;
typed schema and complete command policy; lifecycle and integration instrumentation;
bounded transport; documentation and end-to-end verification. Update the main Skill
with the current Hub policy. Deployment,
public release, and any production policy changes are separate delivery stages.
